# HuntMaps2 quality and usability audit — 2026-10-17

**Disposition: fixes and a fresh passing release check are warranted.** This audit reproduced silent note loss, an untracked-worker launch failure, a source-integrity gap on warm coverage caches, and a damaged-run failure that blocks otherwise valid areas. It also reproduced an inspection confirmation gap, recovery limitations and list responsiveness problems. Eleven findings are confirmed: four P1 and seven P2; P3 recommendations concern guide clarity. No P0 issue was established. Passing existing tests did not establish absence of these defects.

This is an audit of the **current working tree**, based on `main` at `68ac7db`, including its pre-existing modified and untracked connectivity/workflow files. It is not an audit of HEAD alone. No application fixes, dependency changes, cleanup, commits, pushes, new scoring model, route optimization or analytical regeneration of owner results were performed.

## Scope, evidence and interpretation

Read `AGENTS.md`, `START_HERE.md`, the glassing specification/plan/status, GUI maintenance/testing/workflow guidance, recent guided scouting, connectivity, lidar recovery, scene storage and performance reports. Reviewed frontend state/effects, polling, coverage, approach review, scene loading and saving; backend catalog, source validation, jobs, storage, working waypoints, connectivity and approach services; and their test fixtures and browser harness.

All mutations used disposable Ubuntu `/tmp` state/workspaces. The owner's GUI server was not used. Historical results and prepared scenes supplied read-only evidence; synthetic networks were explicitly engineering fixtures. Python work used `.venv/bin/python`; existing Chrome/Playwright and installed frontend tools were used without installs. External browsing was disabled or blocked. No other data partitions were used.

Evidence directory: [`/tmp/huntmaps-audit-20261017-9ng51tgv`](/tmp/huntmaps-audit-20261017-9ng51tgv). Standalone reproduction scripts are retained under its [`reproducers/`](/tmp/huntmaps-audit-20261017-9ng51tgv/reproducers). These are audit instruments, not application tests added to the repository. Python reproducers require the repository on `PYTHONPATH`; use `PYTHONDONTWRITEBYTECODE=1`. Fixed fixture subdirectories are deliberately not overwritten on a repeated invocation.

**CONFIRMED** means reproduced through actual application functions/services/browser, sometimes with a stated fault injected at a boundary. **PLAUSIBLE** means code-review concern without a completed reproduction. UX recommendations are judgments supported by observed tasks/layouts, not claims from a user study. Fault injection proves handling of that failure condition, not its incidence in normal use.

Priorities: P0 = immediate broad destructive/catastrophic issue; P1 = silent saved-data loss, untracked execution, misleading integrity or broad availability failure; P2 = consequential recovery, workflow, usability/performance or test-confidence gap; P3 = smaller clarity/polish issue. Effort is a rough engineering estimate including focused regression coverage, not a commitment.

## Confirmed findings

### A01 — P1: out-of-order saves silently lose the newer note

**Reproduction:** use a disposable run, open Setup details, type `old note`, and click Save review. Hold that PUT **before it reaches the server**. Type `new note` and save again. Let the second request succeed, then release the first. Read the annotations endpoint or reload.

**Expected:** the latest acknowledged edit remains saved, or an explicit conflict prevents the older write. **Actual:** the API first held `new note`, then held `old note`; the editor still showed `new note` and **Saved on this computer**. Both saves succeeded. This can also lose decision changes carried in the same payload. Persisted notes feed exports, so the risk extends beyond the displayed editor.

**Location:** [gui/frontend/src/main.tsx:1130](/home/tanner/Desktop/huntmaps2/gui/frontend/src/main.tsx:1130) (`save`, `annotationSaveTicket`) and [huntmaps_gui/api_routes.py:381](/home/tanner/Desktop/huntmaps2/huntmaps_gui/api_routes.py:381) (`annotate`). The ticket protects the UI from an older reply; it does not prevent that request from overwriting storage. Save remains available during an earlier request, and the API has no record revision condition.

**Evidence:** [browser-reproductions.json](/tmp/huntmaps-audit-20261017-9ng51tgv/browser-reproductions.json), [note-race.png](/tmp/huntmaps-audit-20261017-9ng51tgv/note-race.png), `huntmaps2-audit-browser.mjs`. The later connectivity-recovery step in that script timed out on a closed job-history disclosure; that does not invalidate the completed save reproduction.

**Fix / regression:** queue saves by run/candidate, track the submitted draft separately from current edits, and use backend optimistic revisions for multiple tabs. Regress delayed first delivery, delayed first reply, edits while saving, switching candidates/runs, failure/retry, and two independent clients. Verify persisted state after reload, not merely the latest toast. **Effort:** 1–2 days.

### A02 — P1: job-record write failure leaves an untracked process and permits another job

**Reproduction:** in disposable state, patch `huntmaps_gui.jobs.write` to raise `OSError` at the initial job JSON write. Call `Jobs.start` with the normal guarded wrapper and a harmless sleeping subprocess. After the exception, inspect the process and `jobs.list(False)`, then submit another harmless job. The audit script terminated/reaped its test workers afterward.

**Expected:** a failed submission leaves no running unmanaged process; the one-job guard remains effective. **Actual:** the first process remained alive, the job list was empty, there were zero waiter threads, and a second running job was accepted while the first remained alive.

**Location:** `huntmaps_gui/jobs.py`, `Jobs.start`: `Popen` precedes durable `write`; the waiter is registered afterward. `shutdown` enumerates recorded jobs, so this worker is absent from ordinary cancellation/recovery too.

**Impact:** an I/O or permissions failure during registration can leave analysis/download work running after the UI reports failure. Concurrent side effects and excess resource use are plausible consequences; the audit used sleepers and did **not** demonstrate damaged analytical data.

**Evidence:** [job-spawn-reproduction.json](/tmp/huntmaps-audit-20261017-9ng51tgv/job-spawn-reproduction.json), `huntmaps2-audit-job-spawn.py`. This is an injected persistence error, not an actual full-disk incident.

**Fix / regression:** use a durable launch intent and failure cleanup around spawn/identity persistence; on failure kill the exact owned process group, wait, close logs, and preserve a diagnosis. Test failures before spawn, immediately after spawn, at fsync/replace and waiter setup; assert no survivor and no overlapping execution. **Effort:** 1–2 days.

### A03 — P1: warm coverage tiles hide changed target-source bytes

**Reproduction:** use the generated disposable `audit-fixture`; request an actual visible tile to populate its RGBA/PNG caches. Change one byte of its copied `analysis/target.tif`, retaining length and restoring mtime. Construct a fresh `Run` and request the same tile. Independently call `Run.mask`.

**Expected:** the cached display request rejects a changed authoritative target, just as the analytical mask path does. **Actual:** the cached tile returned the identical 1,084 PNG bytes, while `Run.mask` raised `Saved source changed` for that target. This was run against a copied fixture, never an owner raster.

**Location:** [huntmaps_gui/tiles.py:48](/home/tanner/Desktop/huntmaps2/huntmaps_gui/tiles.py:48) (`fingerprint`) and `:84` (`sources`). Target/tree dependencies are included by path/size/mtime; the existing RGBA path skips `run.mask`/`run.cover`, where those inputs would be validated. The stronger inode/ctime checksum-cache keys elsewhere do not help when validation is never called.

**Impact:** the map can present previously valid coverage while the current target evidence fails integrity. This is a confirmed detection gap; it is **not** evidence that the owner's targets or saved scores are presently wrong. The equal-size/equal-mtime condition is explicit.

**Evidence:** `cached_target_corruption` in [backend-reproductions.json](/tmp/huntmaps-audit-20261017-9ng51tgv/backend-reproductions.json), `huntmaps2-audit-backend.py`.

**Fix / regression:** validate all authoritative raster dependencies before consulting display caches and include verified content identity in their keys. Test warm/cold cache parity after same-size/same-mtime target and class-source corruption, manifest changes and atomic replacement. Corruption must fail visibly without rewriting evidence. **Effort:** 1–2 days.

### A04 — P1: a damaged unrelated run blocks the entire catalog and valid run retrieval

**Reproduction:** in a copied fixture workspace, verify `/api/runs` and `/api/runs/audit-fixture` both return 200. Add a separate `results/damaged-unrelated/` containing `manifest.json`, `analysis/scores.json`, and truncated `scouting.json` (`{truncated`). Request both endpoints again.

**Expected:** identify the damaged entry while healthy runs remain available. **Actual:** both endpoints return 400 naming the unrelated damaged configuration. `Run(valid_id)` first scans every candidate run, so direct retrieval does not bypass the failure.

**Location:** [huntmaps_gui/catalog.py:51](/home/tanner/Desktop/huntmaps2/huntmaps_gui/catalog.py:51) (`runs`) and `:171` (`Run.__init__`). Parsing each listing entry has no per-entry error isolation.

**Impact:** a damaged completed-looking run disables normal Open existing work and otherwise valid areas. The error suggests recovery in Storage, although GUI record backups do not contain that analysis configuration.

**Evidence:** [catalog-reproduction.json](/tmp/huntmaps-audit-20261017-9ng51tgv/catalog-reproduction.json), `huntmaps2-audit-catalog.py`.

**Fix / regression:** retain a diagnostic entry for the bad run, isolate its failure, and resolve requested IDs without requiring unrelated configurations to parse. Test valid + truncated JSON, valid JSON with wrong schema, missing inputs and recovery; assert healthy area opening and exports continue. Preserve damaged bytes. **Effort:** 1–2 days.

### A05 — P2: a failed foliage asset still allows a lidar scene to be confirmed

**Reproduction:** in isolated state, shortlist saved A0075 and compute/select an actual approach using an explicitly artificial local network. Open its existing immutable scene while returning HTTP 500 for `cluster-120-dense-vertices.bin`. Wait for `Scene asset unavailable`. Inspect workflow state and click Confirm setup.

**Expected:** a scene whose requested foliage failed remains incomplete, or the user explicitly accepts a clearly labeled degraded terrain-only inspection. **Actual:** the viewer reported the asset failure, camera diagnostics had `loaded:false` and `vegetationVisible:false`, yet viewing was recorded with `fidelity: lidar`; Confirm setup was enabled and the backend persisted `confirmed:true`.

**Location:** [gui/frontend/src/scene-viewer.tsx:588](/home/tanner/Desktop/huntmaps2/gui/frontend/src/scene-viewer.tsx:588) invokes `onOpened` after initiating rendering, before asynchronous foliage rebuild finishes; [gui/frontend/src/first-person.tsx:849](/home/tanner/Desktop/huntmaps2/gui/frontend/src/first-person.tsx:849) records viewing, and its confirmation gate trusts `opened`/`viewedSceneKey`. Fidelity in `huntmaps_gui/workflow.py` derives from prepared fine-ground metadata, not successful requested rendering.

**Impact:** collection evidence can imply completion of an inspection whose vegetation never appeared. Terrain-only inspection is an allowed product behavior; the defect is accepting an unacknowledged render failure as successful current scene viewing.

**Evidence:** [scene-confirm-failure.json](/tmp/huntmaps-audit-20261017-9ng51tgv/scene-confirm-failure.json), [failed scene with enabled confirmation](/tmp/huntmaps-audit-20261017-9ng51tgv/scene-failed-before-confirm.png), `huntmaps2-audit-scene-setup.py` and `huntmaps2-audit-scene-confirm.mjs`. Source scene assets stayed read-only.

**Fix / regression:** expose required/optional scene readiness, surface failures adjacent to confirmation, and record the fidelity actually accepted. Test delayed/failed foliage, failed base geometry, imagery fallback, context loss after viewing and successful retry. Acknowledged terrain fallback must remain possible without falsely claiming loaded foliage. **Effort:** 1–2 days.

### A06 — P2: restoring a backup merges later files without explaining that limitation

**Reproduction:** create a backup in disposable state before any workflow file exists. Shortlist A0001. Restore the earlier backup and fetch workflow state.

**Expected:** a snapshot restore returns to the earlier state, or the UI clearly says it only overwrites files present in that backup and previews retained later records. **Actual:** restore returned success with `restored:0`; A0001 remained shortlisted. New files absent from the backup are untouched. This is a confirmed recovery limitation and misleading operation boundary, not proof that every restore loses data.

**Location:** [huntmaps_gui/maintenance.py:123](/home/tanner/Desktop/huntmaps2/huntmaps_gui/maintenance.py:123) (`restore`) iterates only `info['files']`; `gui/frontend/src/storage-panel.tsx` labels the operation Restore selected backup without explaining merge semantics.

**Evidence:** `restore_new_records` in [backend-reproductions.json](/tmp/huntmaps-audit-20261017-9ng51tgv/backend-reproductions.json).

**Fix / regression:** define snapshot versus merge semantics, show the concrete restore diff, and validate related workflow/waypoint/ready-pointer records as a set. Preserve the automatic pre-restore backup. Test absent-at-backup files, later manual/working points, workflows, references and pending tokens, not only overwriting an existing state file. **Effort:** 1–3 days.

### A07 — P2: structurally damaged job JSON causes 500s while Storage reports no problem

**Reproduction:** in disposable state create a job JSON with the required keys but `started:'bad timestamp'` and a valid hex ID; construct the application and GET `/api/jobs` and `/api/storage`.

**Expected:** surface a damaged-record entry, preserve its bytes and keep healthy job history/recovery available. **Actual:** `/api/jobs` returned 500; Storage returned 200 with `problems:[]`. `Jobs.shutdown` also raised a timestamp subtraction `TypeError`.

**Location:** `huntmaps_gui/jobs.py`, `Jobs.__init__`/`_list` validate key presence but use values without checking types; `huntmaps_gui/maintenance.py:status` checks JSON readability rather than the job schema. The test's active record also passed startup's interruption branch, so damage can be rewritten before it is diagnosed.

**Impact:** unavailable progress/history, blocked maintenance and broken shutdown behavior after valid-JSON corruption. This was a fixture mutation, not discovered owner corruption.

**Evidence:** `malformed_job` in [backend-reproductions.json](/tmp/huntmaps-audit-20261017-9ng51tgv/backend-reproductions.json). An initial audit-instrument attempt surfaced the shutdown exception; the retained completed reproduction explicitly records it.

**Fix / regression:** validate IDs, statuses, timestamps and optional process identities before state transitions; have Storage and Jobs share that validator. Test wrong types, missing values, mixed healthy/damaged history and shutdown/restart without silently resetting or rewriting damage. **Effort:** 1–2 days; share work with A04.

### A09 — P2: ordinary note editing recomputes/renders hidden large candidate lists

**Reproduction:** open the existing **549-location** `scouting-2026-10-16222` through isolated state, choose All evaluated setups, open Setup details and type `Check branches here.` with sequential keyboard events. No save is needed. Repeat the same action on the 24-point synthetic fixture.

**Evidence:** [real-interactions.json](/tmp/huntmaps-audit-20261017-9ng51tgv/real-interactions.json), [small-interactions.json](/tmp/huntmaps-audit-20261017-9ng51tgv/small-interactions.json), `real549` in [ui-extra.json](/tmp/huntmaps-audit-20261017-9ng51tgv/ui-extra.json).

**Fix / regression:** index filter/rank/ID lookups, compute maximum coverage once, memoize list data and avoid constructing hidden cards. Consider windowing after profiling. Measure keyboard input, filter/sort, polling and selection at 150/600/1,500/5,000 candidates with/without target filters; enforce an agreed input-to-paint budget and verify identical ranking/selection/coordinates. **Effort:** 2–4 days. A separate initial synthetic scale instrument had an incorrect `<100` wait for exactly 100 matches; its timeouts are excluded from product findings.

### A11 — P2: stalled browsing tiles can exhaust the shared API worker pool

**Reproduction:** create the real FastAPI app with disposable state and an HTTPX ASGI client. Hold the transportation provider read behind a bounded event; submit 40 distinct valid transportation tile GETs. Once all 40 worker tokens are borrowed, request `/api/jobs`. Release the provider after a two-second observation window and join all requests. No external request is made.

**Expected:** optional browsing traffic cannot prevent lightweight job status and recovery requests from being serviced. **Actual:** only two requests entered the provider, but all 40 shared worker tokens were borrowed: the remaining tile handlers blocked on `browsing.WORKERS`. The jobs request remained incomplete throughout the blocked-provider window, then completed after release. An idle jobs request completed normally. The idle jobs read took 13 ms; the blocked read took 2,016 ms after the deliberately two-second hold. Exact timings are in the retained JSON.

**Location:** `huntmaps_gui/browsing.py:transportation` acquires a blocking semaphore inside a synchronous route, `/api/browsing/transportation/...` in `api_routes.py`. These handlers consume the same AnyIO worker capacity as synchronous Jobs and scouting endpoints.

**Impact / boundary:** pending optional context requests can delay progress, cancellation and ordinary scouting APIs during provider stalls. Forty outstanding requests can arise across tabs or repeated requests; this audit did not establish that a single idle viewport dispatches 40 concurrent image requests. The real provider's 12-second request timeout is code-reviewed, not an observed outage duration here.

**Evidence:** [browsing-starvation.json](/tmp/huntmaps-audit-20261017-9ng51tgv/browsing-starvation.json), `huntmaps2-audit-browsing-starvation.py`. This is a confirmed service concurrency reproduction with an injected stalled provider, not a live-provider benchmark.

**Fix / regression:** admit only a bounded number of browsing requests before they occupy shared workers, or await provider capacity without blocking that pool; isolate optional provider work and keep a short failure/retry policy. Test a stalled tile burst while status, cancellation and local scouting reads must remain responsive. Include disconnected clients/rapid panning and multiple tabs. **Effort:** 1–3 days.

## Plausible risks requiring follow-up, not confirmed bugs

- **Multi-file restore interruption:** some restored workflow/network/scenario files use direct `write_bytes`, unlike atomic JSON replacement. A crash can potentially leave mixed generations. A06 establishes merge behavior, not this crash outcome. Inject interruption between/within restoration writes before choosing a transactional design.
- **Scene resource retention after repeated open/close:** disposal exists, but the existing performance browser checks focus on idle redraws and movement geometry requests. Establish browser heap/GPU baselines across repeated full-scene cycles before claiming a leak or adding cache changes.
- **Larger filtered lists:** source review identifies nested scans with unfavorable growth; A09 establishes real 549-point friction. The 1,500/5,000 active-filter UI and full 5,000-view scoring runtimes were not established. Resource guards remain meaningful and should not be loosened based on extrapolation.
- **Displayed working-point matching rank:** connectivity snapshot refreshes working raw area but can inherit original `matching_km2` when no freshly applied filter supplies a current value. Validate ranking against a moved point's current masks before calling this a numerical defect; no changed scoring output is asserted here.
